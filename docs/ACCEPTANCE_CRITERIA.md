## How to read this document

- Each criterion has a stable ID (`AC-<AREA>-nn`). Revision-1 IDs keep their numbers. New criteria take the next free numbers.
- Every criterion has a tag: `[Traces: <requirement IDs>]`, or `[Traces: <requirement IDs>; Source: <team doc section>]` when a team doc supplies the expected value. A criterion that only tests a team default with no LOCKED requirement behind it is traced as `—`.
- Each criterion uses **Given / When / Then** and checks one behavior. A "scenario outline" runs the same check once per listed example, and each example passes or fails on its own.
- Terms:
  - **Staff**: an authenticated internal user with the Administrator ("Admin") or Agent role.
  - **Customer**: anyone using the public website (the Portal). Customers have no accounts.
  - **Secure link**: a link the system emails to a customer for one ticket (Q1). Its shape is `https://<domain>/t#<token>` (ARCHITECTURE §8). Using it starts a customer access session for that one ticket.
  - **Lookup link** (60 minutes), **notification link** (7 days), and **Resolved link** (valid until that ticket's auto-close due time) are the three secure-link lifetimes (ARCHITECTURE §8).
  - **Direct backend request**: a request sent straight to the API (`/api/v1`), bypassing the Console or Portal UI. It checks that rules are enforced in the backend (P17).
  - **Denied**: the action has no effect. No state changes, nothing is stored, and no protected data appears in the response. The response is an RFC 9457 Problem Details body with a stable `code` and no stack trace (ARCHITECTURE §6.2). Where a criterion names a code, the tester also checks the code.
  - **Not offered**: the UI shows no control for the action.
  - **Active states**: New, Open, In Progress, Waiting on Customer, Resolved. **Terminal states**: Closed, Cancelled (ARCHITECTURE §4).
  - **T**: a timestamp from the controllable test clock (`POST /api/v1/test/clock`, test environment only). **336 hours** = 14 × 24 hours (P4).
  - **TBD: wording pending Designer/Support Ops pass** (none left as of revision 10): the exact text will be taken from EMAIL_AND_WORDING (emails) or DESIGN (screens) after the Designer/Support Ops pass. Until then, only the non-wording parts of the criterion are checked.
  - **Privacy feature off / on**: the privacy notice link and acknowledgement checkbox are off by default and can be switched on through configuration (B10). Criteria in (h) say which state they need.
  - **TBD: Architect**: a mechanic (such as an error code) the Architect still has to define.
  - **TBD (OQ-n)**: a part left open by an Open Question. The rest of the criterion still applies.
  - Times in expected results are America/New_York, written "ET".

### Criteria: staff-driven transitions

- **AC-LC-01** `[Traces: §10, P9]` **Given** a customer has just submitted a valid ticket **When** staff open that ticket **Then** its status is New and it has no assignee.
- **AC-LC-02** `[Traces: §6, §10, R3; Source: ARCHITECTURE §4]` **Given** a New ticket **When** an Agent accepts it **Then** its status becomes Open, the assignee is that Agent, and an acceptance date/time is recorded.
- **AC-LC-03** `[Traces: §6, §10, R3; Source: ARCHITECTURE §4]` **Given** a New ticket **When** the Admin assigns it to an Agent **Then** its status becomes Open, the assignee is that Agent, and an assignment date/time is recorded.
- **AC-LC-04** `[Traces: §10, R3]` **Given** an Open ticket **When** an Agent changes its status to In Progress **Then** the status is In Progress.
- **AC-LC-05** `[Traces: §10, R3]` **Given** an In Progress ticket **When** an Agent changes its status to Waiting on Customer **Then** the status is Waiting on Customer.
- **AC-LC-06** `[Traces: §10, R3]` **Given** an In Progress ticket **When** an Agent changes its status to Resolved **Then** the status is Resolved.
- **AC-LC-07** `[Traces: §11, R3; Source: ARCHITECTURE §4, G5; DESIGN 2.4, OQ-29]` *Scenario outline.* **Given** a ticket in state *S* **When** staff member *U* sets its status to *T* **Then** the status is *T*. Run every combination: *S* ∈ {New, Open, In Progress, Waiting on Customer, Resolved}; *T* ∈ {Open, In Progress, Waiting on Customer, Resolved}, *T* ≠ *S*; *U* ∈ {Agent, Admin}.
- **AC-LC-08** `[Traces: §11, R3, P4; Source: ARCHITECTURE §4]` **Given** a Resolved ticket **When** an Agent moves it back to In Progress **Then** the status is In Progress and the staff ticket view shows "Auto-closes: —".

- **AC-LC-33** `[Traces: §10, R3; Source: ARCHITECTURE §4; DESIGN 2.4]` *Scenario outline.* **Given** a ticket in state *S* **When** staff look at the status choices and also send a direct backend request to set status New **Then** New is not offered, the request is denied (code `INVALID_TRANSITION`), and the status is still *S*. Examples *S*: Open, In Progress, Waiting on Customer, Resolved.
- **AC-LC-34** `[Traces: P4, §10; Source: ARCHITECTURE §4, G5; DESIGN 2.4]` **Given** a Resolved ticket **When** an Agent or the Admin looks at the status choices and also sends a direct backend request to set status Closed **Then** Closed is not offered, the request is denied, and the ticket is still Resolved.
- **AC-LC-35** `[Traces: §10, R3; Source: ARCHITECTURE §4, G5; DESIGN 2.4, W-07c]` *Scenario outline.* **Given** a ticket in state *S* **When** staff member *U* cancels it and confirms **Then** the status becomes Cancelled. - **AC-LC-37** `[Traces: R3, §6; Source: ARCHITECTURE §4; REQUIREMENTS_DISCOVERY T1]` *Scenario outline.* **Given** a ticket in state *S* **When** an Agent or the Admin sends a direct backend request to accept, assign, reassign, or unassign it **Then** the request is denied and the assignee and status are unchanged. ## (d) Emails: sent and not sent

All checks use the captured outbox (Mailpit; see Test Strategy). "Customer" email = the ticket's submitter email. Admin-alert recipients (B7): new-ticket alerts go to every active Administrator; reply and reopen alerts go to the assignee, or to every active Administrator if the ticket is unassigned. A customer cancel also sends a staff alert, routed the same way (T14). Customer emails include the support reply text, and internal information never goes in customer emails; staff alerts may show status, priority, assignee, and impact, but never internal note text (B8, T11). Staff alerts carry a preview of the customer's message and a clickable link to the ticket (T15). Every email sent outside production has a `[TEST]` subject tag (T16). Email text comes from EMAIL_AND_WORDING and mechanics from ARCHITECTURE (REQUIREMENTS_DISCOVERY T4). Exact email wording checks use EMAIL_AND_WORDING pass 5 (AC-EM-34, -36, -37).

## (i) Spam protection

## (j) Auto-close timing

Rule (ARCHITECTURE §4, §10; ADR 0010): `auto_close_due_at` = time of the most recent move into Resolved + (reopen window in days × 24 h), using the window in effect at that moment. The window is limited to 1–14 days (REQUIREMENTS_DISCOVERY T2), so the Resolved link never outlives R9's 14 days. The auto-close job runs every 15 minutes (`*/15 * * * *`), so a ticket due at T + 336 h must be Closed by T + 336 h 15 min. A customer reopen is allowed only while now < `auto_close_due_at`. All checks use the controllable test clock with the default 14-day window unless stated.

- **AC-CLOSE-01** `[Traces: P4, §11; Source: ARCHITECTURE §10]` **Given** a ticket moved into Resolved at T **When** the clock is at T + 336 h minus 1 minute and every scheduled run up to then has happened **Then** the ticket is still Resolved.
- **AC-CLOSE-02** `[Traces: P4, §11; Source: ARCHITECTURE §10; ADR 0010]` **Given** a ticket moved into Resolved at T and left alone **When** the clock reaches T + 336 h 15 min with the 15-minute runs happening **Then** the ticket is Closed.
- **AC-CLOSE-03** `[Traces: §11, §10]` **Given** a ticket moved into Resolved at T **When** the customer reopens it at T + 336 h minus 1 minute **Then** the reopen succeeds and the status is Open.
- **AC-CLOSE-04** `[Traces: P4]` **Given** a ticket Resolved at T1, reopened by the customer, and Resolved again at T2 (at least 2 h after T1) **When** the clock reaches T1 + 336 h 15 min **Then** the ticket is still Resolved.
- **AC-CLOSE-05** `[Traces: P4; Source: ADR 0010]` **Given** the ticket from AC-CLOSE-04 **When** the clock reaches T2 + 336 h 15 min **Then** the ticket is Closed.
- **AC-CLOSE-06** `[Traces: P4; Source: ARCHITECTURE §4]` **Given** a ticket Resolved at T1 that staff move back to In Progress and then to Resolved again at T2 (at least 2 h after T1) **When** the clock reaches T1 + 336 h 15 min **Then** the ticket is still Resolved (the clock counts from the most recent move into Resolved).

- **AC-CLOSE-08** `[Traces: P4]` **Given** a ticket Resolved at T and reopened by the customer at T + 1 h **When** the clock passes T + 336 h 15 min **Then** the ticket is still Open.
- **AC-CLOSE-09** `[Traces: R1, P4; Source: ARCHITECTURE §4]` **Given** a ticket Resolved at T and replied to by the customer at T + 24 h (no reopen) **When** the clock reaches T + 336 h 15 min **Then** the ticket is Closed (the reply did not move the due time).

### Time control

- All time-based ACs use the test clock: `HD_ENV=test` with `HD_TEST_CLOCK_ENABLED=true` exposes `POST /api/v1/test/clock` (ARCHITECTURE §10). Production config must refuse this flag (AC-OPS-21).
- Auto-close runs every 15 minutes (`*/15 * * * *`, ADR 0010). Boundary tests move the clock to T + 336 h − 1 min (still Resolved), then to T + 336 h 15 min, and trigger the job (`hd run-job auto-close --now=<time>` or the pg-boss schedule) to assert Closed. The "deadline" for each AC is due time + 15 min. Separately, one stack test checks the job's schedule really is `*/15 * * * *`.
- Reopen-at-boundary (AC-CLOSE-13) runs the reopen at due + 1 min **without** running the job, to prove the reopen rule doesn't depend on job timing.
- Link lifetimes: boundary tests at 59 / 61 minutes (lookup), 7 days ± 1 minute (notification), and due ± 1 minute (Resolved link). "Sent at T" is the worker's send time, because tokens are created at send time.
- Reopen-window boundaries (T2): unit and API tests save 1 and 14 (accepted) and 0 and 15 (rejected), and run the auto-close boundary for W = 1 and W = 14 (AC-CLOSE-14, -16, -21). AC-LINK-17 checks link expiry under both.
- Daylight saving: AC-CLOSE-17 and AC-GEN-02 pin instants across the Nov 1, 2026 change.

### Email

- All email ACs read Mailpit's API in test. Assertions: recipient, count per event, presence/absence of text, link target and expiry, headers (From, Reply-To, In-Reply-To/References), no remote images.
- The test environment runs with `HD_ENV=test`, so every subject starts with `[TEST]` (T16). Subject checks strip that tag first, and AC-EM-45 checks it on its own, including one production-mode instance.
- Admin-alert recipients (B7) are tested with a fixed cast: two active Administrators, one turned-off Administrator, and two Agents. Each alert AC asserts the exact recipient set (AC-EM-08 to -11, -38 to -40).
- AC-OPS-07, -08, -12, -13 run once against the real Gmail mailbox in the pre-launch environment and once after any provider switch. They aren't part of every CI run (Gmail's ~500/day limit).
- Subjects (T10): AC-EM-35 compares the lookup and new-link email subjects against the ticket subject. AC-EM-37 checks the admin-alert subject format with a regex (`^\[Help Desk\] .+ HD-[A-Z0-9]{6}: `) until the exact event words are confirmed.
- Threading (T4): AC-EM-33 compares the Subject, `Message-ID`, `In-Reply-To`, and `References` headers across every customer email for one ticket.
- Sender change (T6): AC-SET-04 to -06 make Mailpit reject one recipient/sender to force a failed test email, then confirm the old From address is still used.
- The SMTP outage test (AC-EM-31) stops Mailpit, performs the action, restarts Mailpit, and checks for exactly one delivery.

### Attachments

- Integration tests use the `fake` scanner for speed and real ClamAV in CI for AC-ATT-10, -11, -21, -23 with the EICAR test file and a password-protected ZIP. AC-ATT-23 stops clamd and moves the clock through the retry window.
- Boundary files are generated with exact byte sizes (10,485,760 and 10,485,761). Over-limit tests (T7) send one bad file plus one good file, and check that nothing at all is stored.

### CAPTCHA and rate limits

- ALTCHA runs self-hosted in test. Tests that aren't about CAPTCHA solve the challenge in the harness. `CAPTCHA_PROVIDER=none` may be used only in dev/test (ADR 0015) and never for AC-SPAM-01, -02, -07.
- Rate-limit tests set distinct client IPs through the test harness and reset limiter state between tests.

### Backups

- CI: backup → wipe → restore → verify counts and hashes (ARCHITECTURE §16.2).
- Weekly in each deployed environment: Sunday 05:00 ET `hd restore-test` (AC-OPS-15). A failed run must alert (AC-OPS-16).

### Staff identity and link purposes (T26b, T25)

- The staff-identity canary (AC-VIS-17, ARCHITECTURE TM-33) runs as an E2E test: a seeded staff user with unique name/email/ID acts on a ticket, and every customer API response, Portal page, and Mailpit email is searched for those values.
- Link-purpose tests (AC-EM-49, -51) use the test clock to check both expiries of the two-link staff reply on a Resolved ticket, and the single reopen link in the Resolved email.
- Preview tests (AC-EM-44, -52) cover 499/500/501 characters, a 600-character word, and `EMAIL_ALERT_PREVIEW_CHARS` at 100, 500, and 501.

### Public submission API (B5)

- AC-API-01 to -08 run with a plain HTTP client (Vitest + `inject`, and Playwright `request`) that never loads the Portal, so the API path is proven on its own. The client fetches and solves the ALTCHA challenge itself.
- The validation, CAPTCHA, rate-limit, attachment, and privacy suites (AC-FORM, AC-SPAM, AC-ATT, AC-PRIV) run once through the Portal and once through the API client.
- AC-API-07 serves a test page from a second origin in Playwright, once with that origin in `PUBLIC_CORS_ORIGINS` and once with it empty. Idempotency tests (AC-API-11 to -13) hold the first request open with a slow multipart upload.

### Privacy feature states (B10)

- The (h) suite runs twice: with the default configuration (feature off: AC-PRIV-25 to -27, -29, -31, -32, -11, -24) and with the feature switched on (AC-PRIV-01 to -03, -13 to -15, -28, -29, -11, -24). Export/erase and the no-tracking-cookie checks run in both.

### Backup location (B2)

- CI sets `BACKUP_TARGET_DIR` to a local directory with the marker file (AC-OPS-05). Removing the marker gives the "drive not mounted" case (AC-OPS-37), and a small tmpfs gives the low-space case (AC-OPS-39). A bind-mounted volume stands in for a mounted drive (AC-OPS-29). A read-only mount gives the unwritable case (AC-OPS-32). No cloud credentials are present in any backup test (AC-OPS-31).

### Repository safety (B1)

- gitleaks runs over the full history on every CI run (AC-OPS-34). The workflow-trigger check (AC-OPS-35) is a review item backed by a small script that parses `.github/workflows/*.yml`.

### Data and isolation

- Each test seeds its own tickets through the public and internal APIs (not by writing to the database), so the rules under test are exercised. DB inspection is used only to prove absence (AC-PRIV-21, AC-ATT-14) or trigger behavior (AC-AUD-17).
- Raw-response checks (AC-VIS-08 to -11) scan the full JSON for note text, priority values, assignee names, and the flag.

### TBD handling

- Parts marked **TBD: wording pending Designer/Support Ops pass** check everything except exact text. They get exact-text assertions after the Designer/Support Ops pass. As of revision 10 no criterion carries this marker; every exact-text check is filled from DESIGN rev 8, EMAIL_AND_WORDING pass 5, or ARCHITECTURE. One **TBD: Architect** part remains (the error code in AC-LC-72, after T35), and as of revision 10.1 no **TBD (OQ-n)** parts remain.

- Parts marked **TBD (OQ-n)** are kept as skipped tests with that reason, so they show up in every test report until the question is answered. Nothing is pending with Brandon any more. The rest of each criterion runs normally.
